## Architecture

StockPros is a monorepo with three services:

| Service        | Stack                                               | Purpose                                          |
| -------------- | --------------------------------------------------- | ------------------------------------------------ |
| **Frontend**   | React 18, TypeScript, Vite, Tailwind CSS, shadcn/ui | Interactive dashboards, charts, and real-time UI |
| **Backend**    | Node.js, Express 5, Prisma, PostgreSQL, Redis       | REST API, auth, market data, background jobs     |
| **AI Service** | Python 3.11, FastAPI, TensorFlow, scikit-learn      | ML-powered time-series stock forecasting (GRU)   |

The backend follows a **modular monolith** pattern — a single deployable process composed from independent business modules with enforced boundary rules. See [backend/ARCHITECTURE.md](backend/ARCHITECTURE.md) for details.

#### Key Architectural Patterns

- **Modular Monolith**: Node.js backend separated into domain modules with enforced boundary checks (`npm run architecture:check`): modules talk only through each other's `index.ts`/`public.ts`, and the `shared/` layer may not import any module (module collaborators, e.g. the Socket.io server's market feed and alert evaluator, are injected from `src/index.ts`).
- **Event-Driven & Decoupled Workers**: BullMQ queues handle email notifications and asynchronous alert tasks.
- **Session-Bound Access Tokens**: every access token carries the id of its session (`sid`), and the auth middleware (and the Socket.io handshake) validate that session on each request, so logout, breach response and staff "invalidate sessions" take effect on the very next call instead of when the token expires. Tokens minted before this change are still honoured for one access-token lifetime (see `resolveLegacyUser` in `backend/src/modules/auth/middleware.ts`, to be deleted afterwards).
- **Real-Time Streaming**: Finnhub WebSocket trades streamed via Socket.io directly to connected clients.
- **Shared Runtime State**: rate limiters use Redis whenever it is connected (chosen per request, falling back to memory), and the emergency market halt is synced across instances through Redis (`shared/infrastructure/emergency-sync.ts`).
- **AI Proxy Pattern**: Python FastAPI service isolates heavy GRU ML inference and caching behind the backend.
- **Multi-Tier Caching**: In-memory and Redis TTL caching for stock quotes, logos, and ML forecasts.

### Data Flow Summary

| Flow             | Path                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| **Live Prices**  | Finnhub WSS → FinnhubService → PriceCache → Socket.io → Browser           |
| **REST Quotes**  | Browser → Backend → Yahoo Finance REST → Response                         |
| **Alert Firing** | Finnhub trade tick → AlertEvaluator → Socket.io room + Email queue        |
| **AI Forecast**  | Browser → Backend `/api/forecast` → FastAPI GRU model → cached prediction |
| **News Ingest**  | NewsCron (\*/15 min) → Polygon.io → PostgreSQL                            |
| **Auth**         | Browser → `/api/auth` → JWT cookies / Google OAuth 2.0                    |
| **Email**        | Alert/Auth event → BullMQ → EmailWorker → SMTP / Resend                   |

## Features

- **Authentication** — JWT sessions, magic-link login, Google OAuth, optional WhatsApp OTP phone verification for Pakistani (+92) numbers via SendPK
- **Real-Time Market Data** — Live quotes via Finnhub WebSocket, historical data from Polygon.io, Twelve Data, FMP, and Yahoo Finance
- **AI Forecasting** — GRU-based time-series predictions with evaluation metrics (MSE, RMSE, MAE), exportable as CSV or PDF reports
- **Dashboard** — Portfolio summary, market overview, and activity feeds
- **Decision Support** — Per-stock buy/sell/hold recommendations with confidence scores, risk levels, and exposure analysis
- **Watchlist** — Track symbols with AI-suggested entry, take-profit, and stop-loss levels; configure 12 alert types (price, percentage, earnings, analyst changes, SEC filings, etc.)
- **News Aggregation** — Multi-source articles with sentiment analysis, category classification, read tracking, and bookmarks
- **Notifications** — Persisted market-interest and delivery preferences; users can independently control in-app alerts, email volatility alerts, and the weekday pre-market digest
- **Role-Based Access Control** — Admin, Portfolio Manager, and Analyst roles with screen-level CRUD permissions. The Roles screen (`/access-control/roles`) creates roles (`POST /rbac/roles`), edits the permission matrix by saving the difference (`POST /rbac/assign-permissions` for what was ticked, then `DELETE /rbac/revoke-permissions` for what was unticked, because assigning only adds) and can enable a supported action that has no permission row yet (`POST /rbac/resource-mappings`). The Users screen replaces a user's roles with `POST /rbac/assign-role` (which needs at least one role) and removes every role with `DELETE /rbac/roles/:roleId` (body `{ userId, roleId }`; it removes the role from that user, it does not delete the role).
- **Search** — Symbol and company lookup
- **Free/Pro Plan Tiers** *(off by default, see below)* — self-serve `/plans` page and `POST /api/v1/auth/plan`; Free is capped on AI forecasts (1/day), decision support (watchlist symbols only), watchlist size (10 symbols), portfolios (1), and real-time quotes (15-min delayed); Pro is unlimited on watchlist size, portfolios and real-time quotes, and includes 300 AI signals (forecasts + market decisions) per billing cycle, after which each extra signal is paid from prepaid credits (see the Team/credits bullet below). Gating runs in parallel to RBAC, toggled per-environment by `config.features.pricingTiersEnabled` (`backend/src/config/{development,production,test}.ts`) — off, the app behaves exactly as RBAC-only; on, tier checks replace RBAC checks for these customer-facing routes only (admin/RBAC-management endpoints are unaffected either way)
- **Safepay Payments & Subscription Renewal** *(off by default, see below)* — Pro tier (Rs 5,999/mo) checkout via Safepay's hosted page (JazzCash, Easypaisa, and cards), confirmed asynchronously via a signed webhook (`POST /api/v1/payments/safepay/webhook`, `x-sfpy-signature` HMAC-SHA512). Toggled independently of pricing tiers by `config.features.enablePaymentProcessor` — off ("Bypass Mode"), upgrading to Pro calls `POST /api/v1/auth/plan` directly with no payment step; on ("Payment Mode"), upgrading redirects to Safepay checkout and the plan only changes once the webhook confirms payment. Each PRO checkout (card or wallet) opens a 30-day billing cycle tracked on a `Subscription` row (`GET/POST /api/v1/payments/subscription*`): card subscriptions default to auto-renew on (toggleable); wallet subscriptions (JazzCash/Easypaisa) are always a manual 30-day pass, since neither wallet supports recurring charges. A daily job (`config.features.enableSubscriptionCron`) emails a renewal reminder 3 days before the period ends, then — if unrenewed — moves the subscription into a 2-day grace period before downgrading back to Free. CARD checkout uses Safepay's Plan-based recurring-subscription product (a pre-created merchant-dashboard "Pro Monthly" Plan, `SAFEPAY_PRO_PLAN_ID`): the customer authorizes once and Safepay itself bills the card each cycle, notifying the app via `payment.succeeded`/`payment.failed` webhooks that extend the period or move the subscription into grace, respectively; toggling auto-renew off/on pauses/resumes the Safepay subscription accordingly. **This recurring-card integration is built against Safepay's published SDKs but has not been verified against their live API** — endpoint paths and webhook field names are best-effort (see doc comments in `backend/src/modules/payments/client.ts`); it is fully exercised and deterministic in mock mode (`config.safepay.mockProvider`) but should be confirmed against Safepay's sandbox before relying on it in production.
- **Team Workspaces, Seats & Prepaid Credits** *(same two flags as above)* — a `TEAM` tier (Rs 7,499/seat/month, 2–150 seats; no Enterprise tier) under `/api/v1/teams` (`backend/src/modules/teams/`): create a workspace (`POST /teams`), add seats mid-term (`POST /teams/seats/add`), invite/accept/remove members, claim and DNS-TXT-verify a company domain (a verified domain with `restrictOrgCreation` blocks employees from creating a second workspace and points them to their org admin), workspace-wide AI `orgInstructions` (returned as `orgContext` on forecast and market-decision/radar responses — these endpoints have no LLM system prompt to inject into), workspace/personal preferences (personal overlays workspace defaults), per-member credit caps, shared watchlists/screeners/research notes, `GET /teams/search`, and `GET /teams/analytics`. `POST /payments/create-checkout` accepts `plan: PRO | TEAM | TOPUP` (TEAM takes `seatCount` + `teamName`; TOPUP takes `packId` `PACK_500|PACK_1000|PACK_2500`); every price is derived server-side in integer paisa. In Payment Mode the team (or added seats / credits) is applied inside one DB transaction together with the PENDING→COMPLETED webhook transition, so duplicate Safepay deliveries return 200 without double-crediting; in Bypass Mode `POST /teams` and `/teams/seats/add` apply instantly. **Metering** (only when `pricingTiersEnabled`): FREE keeps its daily quotas; PRO gets 300 AI signals and each TEAM seat 375 (1.25×) per billing cycle (the subscription's `currentPeriodStart`, else the UTC calendar month), counted from `usage_events` for AI forecasts and market decision/radar calls. The quota check and the write (usage event, or spend-cap check + credit deduction + ledger row) run in one transaction under a per-user Postgres advisory lock, so a burst of parallel requests at the boundary cannot overshoot the quota, a member's spend cap, or the balance. Beyond that, the action is paid from prepaid credits (Rs 50/signal) — the user's balance for PRO, the shared team pool for members (subject to the member's `monthlyCreditLimitPaisa`) — with every movement in the append-only `credit_ledger`, else the API answers `403` with `errorCode: OVERAGE_REQUIRED` and `details.canTopUp`. `payment_transactions` and `credit_ledger` carry no foreign keys so the audit trail survives user/team deletion. Invite rows hold the invitee's email, so they are personal data: a daily job (`team-invite-cleanup`, 07:30, alongside the subscription job under `config.features.enableSubscriptionCron`) deletes invites past their expiry, and deleting an account removes any invites addressed to that email; logs record counts only, never addresses. **Logging & PII:** email addresses and phone numbers do not appear in log lines — the mail workers log job / subscription / invite / team ids (the magic-link job has no user id, so only its job id), and the logger scrubs any address or E.164 number that still ends up in a message or field (including provider errors such as "550 <user@x.com> rejected"); the dev-only "inbox" printout (subject and body, so a magic link can be copied locally) is limited to `NODE_ENV=development` and never shows the recipient. Email job payloads read back from Redis are validated with zod (http(s)-only links, known roles/variants) instead of being cast, and a malformed job fails permanently without retries. Team subscriptions are **manual-renewal** (`POST /payments/subscription/renew?scope=TEAM`): Safepay's recurring Plan is fixed-price and cannot bill per-seat, so `auto-renew` with `scope: TEAM` only records a flag; the daily job sends the owner a reminder, then a 2-day grace period, after which the workspace is cancelled and members return to PRO (if they hold a live personal subscription) or FREE. TEAM members are flagged `X-Queue-Priority: HIGH` during the NYSE open/close spike windows (first and last 30 minutes of the session, ET; `backend/src/shared/utils/market-hours.ts` knows the NYSE holiday calendar — New Year's, MLK, Presidents', Good Friday, Memorial, Juneteenth, Independence, Labor, Thanksgiving and Christmas, with weekend-observed shifts — and the 13:00 early closes, so weekends, holidays and closed hours are never flagged). Compute-heavy routes (`GET /forecast`, `GET /decision-support/market/decision/:symbol`, `GET /decision-support/market/radar`) sit behind an in-memory priority limiter (`backend/src/shared/middlewares/priority-queue.ts`, no extra dependency): a flagged Team request is admitted ahead of standard traffic (tier 1 vs 10, FIFO within a tier). It runs after quota/credit checks, so rejected requests never hold a slot, and only the server-set team context counts — a client-sent `X-Queue-Priority` header is ignored. Under a surge, a request that waits longer than `maxWaitMs` or arrives when `maxQueueDepth` are already waiting is shed with `503`. Limits are per process and set in `backend/src/config/{development,production,test}.ts` (`priorityQueue.concurrency` / `maxQueueDepth` / `maxWaitMs`). Forecast and decision support dispatch no BullMQ jobs, so there is no job priority to set. All market-hours maths goes through `Intl.DateTimeFormat` with the explicit `America/New_York` zone (never host-local hours), so EDT/EST changes do not shift the 09:30 open or 16:00 close and results do not depend on the server's TZ. **Ops kill-switch:** `EMERGENCY_MARKET_CLOSED=true` (`config.market.emergencyClosed`, listed in `backend/.env.example`) makes `isNyseMarketOpen()` and `isMarketSpikeWindow()` return `false` regardless of the calendar, for unscheduled exchange halts; it only seeds the initial state at boot (accepts only true/false/1/0; a typo fails startup instead of silently meaning "open"). The live state is an in-memory switch — `isEmergencyClosed()` / `setEmergencyClosed(boolean)` in `market-hours.ts` — so it can be flipped at runtime without a restart (every change is logged; an admin endpoint can call it). It lives in the process's memory, which is right for the app's single-instance deployment (running several instances would need the change broadcast to each). The queue sheds a request after `priorityQueue.maxWaitMs` = 20 s; the frontend HTTP client applies a 40 s timeout to `GET /forecast`, `/market/decision/:symbol` and `/market/radar` (`frontend/src/shared/api/timeouts.ts`), i.e. the queue wait plus 20 s of compute headroom — change the two together. Every unexpired invite reserves a seat: `POST /teams/invites` counts active members + unexpired pending invites against `seatCapacity` under a team-row lock (accepting an invite takes the same lock), so simultaneous admins cannot issue more live links than free seats. `POST /teams/invites` also queues an invite email (`team-invite` job on the existing email queue, with the queue's retries/backoff) and still returns the link plus `emailQueued`; `GET /teams/members` lists members (emails and credit limits are admin-only). **Frontend:** team members see the workspace's AI instructions as a "Workspace guidance" banner on Forecast, Market Analysis and Opportunity Radar; the workspace page also has Search (shared assets + members' saved AI decisions), Preferences (personal overrides and, for admins, workspace defaults; choosing the default option clears the override) and, for admins, a Credits tab with the pool's history; Settings has display preferences for everyone and a Credits tab (your own history, `GET /payments/credits/ledger`) for Pro/Team. **Quota meter:** `GET /api/v1/payments/me/usage` returns the caller's signals used / included for the current cycle (same window and counting as enforcement), the credit pool that pays beyond it (own balance for Pro, shared pool for team members) with whether they may top it up, and any personal spend cap; the UI shows it with a Top up credits button on Settings → Credits, Manage Subscription and the workspace Overview. It is hidden for FREE users (daily quotas apply) and while pricing tiers are not enforced, and the Top up button is disabled with an explanation when online payments are off (there is no checkout to send them to). **Usage detail page:** `/usage` (linked from the quota meter, so also from Settings → Credits) shows the allowance and reset date, AI signals per day as a bar chart (with a table view), a per-feature split (`ai_forecast`, `ai_decision`; unmetered features such as search and the radar are not counted, matching the meter) and the credit ledger. It is backed by `GET /api/v1/payments/me/usage/history?range=current|previous&tz=<IANA zone>` (`backend/src/modules/payments/usage-history.ts`): days are cut with PostgreSQL `date_trunc('day', created_at AT TIME ZONE $tz)` so a signal at 23:30 local time counts for that local day (`tz` defaults to `UTC`; the UI sends the browser's zone; only IANA names are accepted — offsets such as `+05:00` are rejected because PostgreSQL reads them with the opposite sign), and every day of the cycle so far is returned, zero-filled. Scope follows the caller: a Pro user (or a stale TEAM plan with no workspace) sees their own usage, a plain team member sees only their own events inside the workspace, and a workspace owner/admin sees the workspace aggregate (`scope: TEAM`); FREE gets `metered: false`. `current` has no upper bound (as in enforcement); `previous` assumes the last cycle was the same length and ended where this one began, because a subscription stores only its current period. **Personal spending limit:** an individual Pro user can cap their own credit spend per billing cycle on the usage page (`PUT /api/v1/payments/credits/spend-cap` with `{ "monthlyLimitPaisa": 5000..10000000 | null }`, `null` removes it; stored in `users.monthly_credit_limit_paisa`, so run `npm run db:sync` after pulling). It uses the same enforcement path as the workspace per-member cap (`resolveSpendCap` / `sumCreditSpend` in `payments/credits.ts`, checked inside the per-user advisory-locked transaction, so a burst cannot overshoot it); a member's limit always comes from their workspace admin and the personal one is ignored while they are in a workspace (`credits.canSetSpendCap` tells the UI which applies). Included monthly signals are never affected. When the limit stops a paid signal the API answers `403 OVERAGE_REQUIRED` with `details.reason: PERSONAL_SPEND_LIMIT_REACHED` (the admin's cap stays `SPEND_LIMIT_REACHED`), and the app opens a "Spending limit reached" dialog pointing to `/usage` instead of the top-up packs, since more credit would not help. Workspace members and FREE users get `403` from the endpoint; lowering the limit below what is already spent is allowed and simply pauses paid signals until the next cycle. `GET /me/usage` now returns `spendCap` for individuals as well. **Usage warning emails:** after each metered AI signal an individual Pro user is emailed (queue job `usage-alert`, template `email-templates/usage-alert.ts`) when they reach 80% and 100% of the included signals, when the credit balance can pay for fewer than 5 more signals (`LOW_BALANCE_SIGNALS`), and at 90% of their personal spending limit. Each warning goes out once per billing cycle: it is claimed by inserting a row in `usage_alerts` (unique on user + kind + cycle start, so concurrent requests send one email) and the low-balance row is cleared when a top-up lands, so the next dip warns again. The check (`payments/usage-alerts.ts`) runs after the signal is counted, is not awaited by the request and never throws, and a free signal below 80% costs no extra query. Workspace members are not emailed yet. Users can switch the emails off on the usage page (`PUT /api/v1/payments/usage-alerts` with `{ "enabled": boolean }`, stored in `users.usage_alerts_enabled`, returned as `alertsEnabled` by `GET /me/usage`); the new `users.usage_alerts_enabled` column and `usage_alerts` table need `npm run db:sync`. Logs carry the user id only, never the address. Only the theme is applied by the UI today — chart layout and indicators are stored for charts that support them. The Plans page shows the Team tier with a 2–150 seat selector; `/teams` (alias `/settings/team`) is the workspace panel (overview + seat gauge, add seats, credits/renewal, org instructions, analytics, members and credit limits, invites, domain DNS verification, shared watchlists/screeners/notes) and appears in the sidebar as "Workspace" for `plan === 'TEAM'`; `/teams/invite?token=…` accepts an emailed invite; any `403 OVERAGE_REQUIRED` with `canTopUp` opens a credit top-up dialog app-wide (members without top-up rights get a toast asking an admin). **Known gaps:** the priority limiter and the emergency flag are in-memory, which suits the single-instance deployment (they would need a shared store if the app were ever scaled out); the invite link works when opened signed out: `/teams/invite?token=…` (alias `/teams/invites/accept`) parks the token in `sessionStorage` (`pending_invite_token`, with a 24h `localStorage` fallback because a magic link opens in a new tab), and once the user has finished signing in the app accepts it automatically and opens `/teams`; an invite that fails is attempted once and cleared. No new environment variables or secrets were introduced; the webhook keeps its verified HMAC-SHA512 scheme.
- **Internal Staff Ops Panel** *(tier-based workflow only — `pricingTiersEnabled: true`)* — a back-office under `/api/v1/admin` (`backend/src/modules/admin/`) and `/admin` in the UI. While the flag is off every admin route answers `403 FORBIDDEN_FEATURE_DISABLED` and the UI route redirects away. Access is by `User.platformRole` (read from the DB on every request): `SUPPORT_AGENT` (read-only search, webhook/usage/queue inspection, audit log), `PLATFORM_ADMIN` (credit adjustments in whole paisa via `amountPaisa`, domain force-verify, subscription extensions, seat-capacity overrides beyond 150 which also clear any scheduled seat reduction, force-remove member, webhook retry) and `SUPER_ADMIN` (everything, plus plan overrides, session invalidation and the in-memory emergency market halt). Every write needs a `reason` (min 10 chars) plus an optional support-ticket reference (`ticketRef`, e.g. `SUP-1234`; mandatory when `config.admin.requireTicketRef` is on, which production enables, and format-checked whenever supplied) and appends one immutable `admin_audit_logs` row in the same transaction; customer email and name are masked in search results by default (`config.admin.maskCustomerPii`; provider webhook payloads are scrubbed too) and a staff member must request `POST /users/:id/reveal` with a reason and ticket to see them (audited as `CUSTOMER_DATA_REVEALED`; the UI hides them again after a minute); `GET /users/:id/timeline` gives support a newest-first history of one customer from transactional records only (payments, credit movements, sign-ins, workspace changes, staff actions: no product analytics, which live in PostHog); `GET /users/:id/usage` shows a customer's metering position (allowance used, spend limit and this cycle's spend, credit balance, and `blockedReason` when the next AI action would be refused), user search also returns their `monthlyCreditLimitPaisa` and `usageAlertsEnabled`, and team search shows each member's cap and cycle spend; `POST /users/:id/spend-limit` (`PLATFORM_ADMIN`, step-up) sets or removes (`null`) an individual Pro user's own spending limit, always with a `reason` and a `ticketRef`, audited as `SPEND_LIMIT_OVERRIDDEN` with the previous and new limit, after which the customer is emailed both limits and the ticket (best effort, queued after the change commits, so a mail problem never fails it) (FREE users and workspace members are refused: a member's cap belongs to their workspace admin); searches that return customer data (users, teams, webhooks, credit ledger) append a `CUSTOMER_DATA_VIEWED` row listing the returned ids (never the search text) and fail closed if that row cannot be written. There is deliberately no product-usage analytics view: that is PostHog's job, and the panel keeps only billing usage (`GET /billing/credit-ledger`) and queue health. In production every write (and every reveal) also needs a recent step-up check: the staff member requests a 6-digit code by email (`POST /admin/step-up/request`), verifies it (`/admin/step-up/verify`; 5 attempts, 5-minute expiry), and then has `config.admin.stepUpWindowMinutes` (default 15) to act, a window that slides with each successful write; otherwise the API answers `403 STEP_UP_REQUIRED` and the panel prompts and retries automatically. Staff sessions also have an absolute lifetime (`config.admin.sessionMaxAgeHours`, 12 in production, not extended by refresh): past it the session is revoked and the API answers `401 STAFF_SESSION_EXPIRED`, which sends the panel back to sign-in. Optionally (`config.admin.ipAllowlist`, IPs or CIDR ranges; empty by default) the whole panel is restricted to your office/VPN networks, answering `403 ADMIN_IP_NOT_ALLOWED` before authentication; IPv4-mapped IPv6 addresses are normalised and a malformed entry stops the app at boot. This relies on `req.ip` being the true client address, so `trust proxy` in `backend/src/app.ts` (currently one hop) must equal the number of reverse proxies in front of the app. Risky actions (plan override, session invalidation, force-removing a member, the market halt, a spend-limit override, switching an announcement on or off, a credit adjustment of at least `config.admin.alertCreditThresholdPaisa`, and a staff member exhausting their step-up attempts) email `config.admin.alertEmails` after they succeed: identifiers and the ticket only, never customer data, and a delivery problem never affects the action itself (alerts are off while the list is empty). The same actions are also posted to the ops chat channel when `OPS_ALERT_WEBHOOK_URL` is set (see **Operational alerts**). Admin routes are rate limited (120 requests/min per IP, 20 writes/min per staff member) and log identifiers only to Pino. Deleting a staff account resets its `platformRole` to `USER` and clears the IP addresses on its audit rows (the rows themselves are kept, keyed by user id). Downgrading a TEAM user via plan override removes them from their workspace, or is refused with 409 if they own it (transfer ownership first). Staff are created only with `npm run admin:grant -- <email> <ROLE>`. Caveat: the market halt is per-process memory, and webhook diagnostics read `PaymentTransaction` (webhooks rejected for a bad signature are never stored).
- **Team administration (modelled on Claude Team)** — roles are `OWNER` (exactly one, `Team.ownerId` — the primary owner), `ADMIN` and `MEMBER`. Every check goes through one permission table in `backend/src/shared/infrastructure/team-access.ts` (`can(role, TeamPermission.…)`; admins manage members, credits, billing and settings, only the owner changes roles, transfers ownership, deletes or exports), so Enterprise custom roles can later become data instead of code. Endpoints under `/api/v1/teams`: `PATCH /members/:userId/role` (ADMIN ↔ MEMBER, owner only), `POST /ownership/transfer` (target must be a seated, active member — a pending invite is refused — and the old owner stays on as admin), `POST /leave` (the owner must transfer first; admins can no longer remove themselves through `DELETE /members/:userId`), `GET /invites`, `DELETE /invites/:id`, `POST /invites/:id/resend`, `PATCH /` (rename), `DELETE /` (owner only, body `{ confirmName }` must equal the workspace name: the workspace is cancelled, auto-renew off, shared assets/invites/domains purged, **every `TeamMember` row deleted** so members can join another workspace, remaining credit forfeited; payments, the credit ledger and the audit log are kept — `Team.ownerId` is therefore not unique, and only an ACTIVE owned workspace blocks creating a new one; a renewal payment that lands after deletion is recorded but never revives the workspace), `GET /export` (owner-only JSON download: settings, members, domains, assets, paid transactions without gateway payloads, audit log; each section capped at 5,000 rows). **Billing admin:** `PATCH /teams/billing-contact` sets where renewal reminders and receipts go (falls back to the owner); `POST`/`DELETE /teams/seats/reduce` schedules a smaller seat count for the next renewal — nothing is refunded mid-term, renewal bills `max(scheduled, members + pending invites)` and the billed count becomes the capacity, and while a reduction is scheduled invites and invite acceptance are limited to the smaller count (`effectiveSeatCapacity`), so it cannot be outgrown before it lands; `GET /payments/team/transactions` and `GET /payments/team/transactions/:id/receipt` (owner/admin, always registered) list paid transactions and show a receipt with a reference such as `SP-2030-456789AB` (derived from the random tail of the transaction id) — the gateway payload and token are never returned; a receipt email (`payment-receipt` job on the existing email queue) goes to the billing contact after each completed team payment. **Audit log:** every admin action (invites, acceptances, removals, role changes, ownership transfers, setting/domain/credit-limit/billing changes, seat changes, workspace rename/delete/export, subscription expiry) is written to the append-only `team_audit_logs` table inside the same transaction as the action, carrying IDs and enum values only (no names, emails or instruction text), and is readable via `GET /teams/audit-log` (owner/admin, cursor-paginated, `action` filter; a cursor from another workspace is refused). **Tenant isolation tests:** `backend/src/modules/teams/__tests__/tenant-isolation.test.ts` (and its payments counterpart) run every team route as a user of workspace B against workspace A's data in an in-memory database that really applies each query's `where` (`backend/src/__tests__/fake-tenant-db.ts`); a guard fails the suite when a route is added without an isolation case. They prove the queries carry the right `teamId` filters — not that Postgres enforces isolation: no database is involved. Postgres row-level security is staged but not applied (policy SQL in `backend/prisma/rls/`, tenant-scoping helper in `backend/src/shared/infrastructure/tenant-context.ts`, steps and limits in `backend/docs/row-level-security.md`); it stays unverified until it has been run against a disposable database. The Workspace page gains Billing (billing contact, scheduled seat reduction, receipts), Activity (audit log) and Settings (rename, transfer ownership, export, delete) tabs, role changes, pending-invite management and "Leave workspace". A lapsed (non-active) workspace keeps its member rows so a renewal can restore them, but that never traps anyone: accepting an invite or creating a workspace first releases the user's seat in a lapsed one (`releaseLapsedMembership`), and a renewal then restores only the members still attached. Schema changes are additive except `Team.ownerId` losing its unique constraint (apply with `npm run db:sync`).
- **Request to join (backend)** — a verified `TeamDomain` carries a `joinPolicy` (`INVITE_ONLY` default, `REQUEST_APPROVAL`, `AUTO_APPROVE`). Endpoints under `/api/v1/teams`: `GET /join-options` (workspaces the caller could join through their email domain; public mailbox domains never match, and nothing is offered to someone who already has a workspace), `GET`/`DELETE /join-requests/me` (own pending request / cancel it), `POST /join-requests` (rate limited to 5/hour per user; `AUTO_APPROVE` seats the caller at once, `REQUEST_APPROVAL` queues a request and emails the owner and admins; a declined user waits 24 hours; every refusal for a closed or wrong-domain workspace is the same 404 so workspaces cannot be enumerated), `GET /join-requests`, `POST /join-requests/:id/approve` and `/decline` (owner/admin, `MEMBERS_INVITE`; approval re-checks capacity under the team-row lock and returns 409 when there is no free seat), and `PATCH /domains/:domain/join-policy` (owner/admin; the domain must be verified to leave `INVITE_ONLY`). Seats are taken by one shared function (`seatMember` in `modules/teams/service.ts`) used by invite acceptance, auto-approval and approval, so capacity and one-workspace-per-user are enforced identically. Audit actions `JOIN_REQUESTED`, `JOIN_APPROVED`, `JOIN_DECLINED`, `JOIN_POLICY_SET` carry IDs and enums only; requests are purged with the workspace and cascade with the user. Emails ride the existing queue as the `team-join-request` job (`REQUESTED` to admins, `APPROVED`/`DECLINED` to the requester). Schema change is additive (apply with `npm run db:sync`).
- **Request to join (frontend)** — a signed-in user with no workspace whose email is on a verified domain with a non-`INVITE_ONLY` join policy sees a "Workspace found" banner on the Dashboard and the no-workspace Teams page (`JoinWorkspaceBanner`): "Request to join {team}" (`REQUEST_APPROVAL`, then a pending state with Cancel request) or "Join {team}" (`AUTO_APPROVE`, joins at once). Owners/admins set a per-domain join policy on the Domains tab and approve or decline requests under Members → Join requests. E2E: `frontend/e2e/join-request.spec.ts`.
- **Login enforcement (backend)** — a verified `TeamDomain` of a live workspace carries an `authPolicy`: `ANY` (default), `GOOGLE_ONLY` `GOOGLE_WORKSPACE` (Google, and the ID token's `hd` claim must equal the domain) or `SAML_SSO` (see Enterprise SSO). `assertLoginAllowed(email, method, googleHd?)` in `shared/infrastructure/team-access.ts` is enforced at every entry point: `generateMagicLink` and `verifyMagicLink` (a link issued before a policy change is refused too), `googleLogin`, and `completeOnboardingFlow` (the onboarding token carries the proof method and `hd`; a token without a recognised method counts as the weakest method and is refused on a restricted domain). **`POST /auth/onboarding` only ever creates an account from an onboarding token** (issued after a verified magic link or Google sign-in); an `email` in the body is not accepted at all, and with no valid onboarding token or access token the call is `401` and creates nothing. An onboarding token can never act as a bearer token (tokens carrying a `type` claim are refused). A refusal is `403` with `errorCode: LOGIN_METHOD_REQUIRED`. `POST /api/v1/auth/login-options` ({ email }) returns only `{ authPolicy, ssoAvailable }` (always `ANY` and `false` for unknown or public domains, login-rate-limited) so the login screen can steer users to Google or SSO. Sessions now record how they signed in (`user_sessions.login_method`, `google_hd`); sessions that predate this have no method and are treated as non-compliant by any restricted domain (fail closed). `PATCH /api/v1/teams/domains/:domain/auth-policy` is **owner only** (`TeamPermission.SECURITY_MANAGE`): a stricter policy needs the domain typed back as `confirmDomain`, the domain must be verified, and if the owner's own email is on the domain their current session must already satisfy the new policy (409 otherwise, so they cannot lock themselves out); it then immediately signs out every non-compliant session of users on that domain except the owner's current one and reports `revokedSessions` (audit action `AUTH_POLICY_SET`). `refreshAccessToken` re-checks the policy as a backstop, revoking a non-compliant session on its next refresh. **Staff recovery:** `POST /api/v1/admin/teams/domains/:domain/reset-auth-policy` (platform admin, step-up, `reason`/`ticketRef`) puts a domain back to `ANY`; it writes both audit trails (`AUTH_POLICY_RESET`) and sends the risky-action alert email. Schema changes are additive (apply with `npm run db:sync`).
- **Enterprise SSO (backend, SAML 2.0)** — dark behind `config.features.enableSso` (off by default; every SSO route answers `403 FORBIDDEN_FEATURE_DISABLED` while off; needs `API_PUBLIC_URL`, and Redis in production). All SAML work sits behind the `SsoProvider` port (`modules/sso/provider.ts`); the adapter is `@node-saml/node-saml` (`modules/sso/providers/node-saml.ts`) so a hosted broker could replace it without touching callers. A verified domain gets a tenant (`team_domains.sso_tenant_id`, the domain's id) and one `team_sso_connections` row (public IdP settings only, no secrets). The adapter requires a **signed assertion** answering a request we issued (`InResponseTo`, single-use, tenant-scoped, atomically claimed), checks audience and clock skew, and returns only a verified identity. **Team routes** (`/api/v1/teams`, `TeamPermission.SSO_MANAGE`: owners and admins): `GET`/`PUT`/`DELETE /domains/:domain/sso`, `PATCH /domains/:domain/sso/enabled`, `POST /domains/:domain/sso/test`. **Switching SSO on is owner only** (`SECURITY_MANAGE`): whoever controls the IdP settings can assert any email on the domain, so an admin who may configure and test it cannot also enable it; admins can switch it off. Runbook, rollout and IdP verification checklist: `backend/docs/sso.md`. `PUT` takes `METADATA_XML`, `METADATA_URL` (https, public addresses only, including IP literals, no redirects, 5s/256KB) or `MANUAL`; any change switches SSO off and clears the test result. Enabling needs a passing test; the admin who passes the test gets their own session upgraded to an SSO session. **Requiring SSO** is the owner-only `PATCH /domains/:domain/auth-policy` with `SAML_SSO` (needs an enabled, tested connection and an SSO owner session; changing or removing the connection is refused while it is required). **Login routes** (`/api/v1/auth/sso`, `ssoLimiter`): `POST /start` ({ email } -> IdP redirect + browser-held `bindingToken`), `POST /:tenantId/acs` (the IdP's form post; always 303 back to the app, failures are logged not shown), `POST /exchange` ({ code, bindingToken } -> the same login result as Google, `sid` claim and refresh cookie included). The one-time code lasts 60 seconds and works only with the binding token of the browser that started the flow. `auth/service.ts` `ssoSignIn` is the single place an identity becomes a session: it requires the asserted email to be on exactly the tenant's verified domain, then calls `assertLoginAllowed` and `persistSession` (recording `login_method = SSO` and `sso_tenant_id`). Audit actions: `SAML_CONFIG_UPDATED`, `SAML_ENABLED`, `SAML_DISABLED` (team log). Apply the schema with `npm run db:sync`.
- **Login enforcement (frontend)** — on `/login` the typed email is checked (debounced) against `POST /auth/login-options`; a `GOOGLE_ONLY`/`GOOGLE_WORKSPACE` domain shows an inline notice, highlights the Google button and disables magic-link, and a `403 LOGIN_METHOD_REQUIRED` from magic-link, `/auth/verify` or Google is shown as that message. Workspace owners set the per-domain policy on the Security tab (`PATCH /teams/domains/:domain/auth-policy`; stricter policies require typing the domain, and the result reports sessions signed out); staff can "Reset auth policy to ANY" in the admin Team workspaces tab (shown only for verified domains whose `authPolicy` is not `ANY`, which the admin team search now returns). E2E: `frontend/e2e/login-enforcement.spec.ts`.
- **Enterprise SSO (frontend)** — `/login` reads `{ authPolicy, ssoAvailable }` from `POST /auth/login-options` (`useLoginOptions`, debounced). When the domain has SSO, **Continue with SSO** appears next to the magic link; when it *requires* SSO (`SAML_SSO`) the notice says so, the magic-link button is disabled, the Google button is dimmed and SSO is highlighted. The button calls `POST /auth/sso/start`, keeps the returned `bindingToken` in `sessionStorage` (`utils/sso.ts`, guarded for private mode) and sends the browser to the IdP only if the URL is https. The IdP's POST to the ACS URL ends in a redirect to **`/auth/sso/complete?code=…`** (`SsoComplete`), which exchanges the one-time code together with the stored binding token (`POST /auth/sso/exchange`) and then behaves like Google sign-in: new users go to onboarding, phone verification takes priority, everyone else lands on their home screen. A code opened in a browser that did not start the sign-in has no binding token and is refused without calling the API. A failed round trip returns to `/login?sso=failed` with a generic notice (the reason is only in the server logs). The shared post-sign-in steps live in `useFinishLogin` and `useRedirectWhenSignedIn`, used by both Google and SSO. E2E: `frontend/e2e/sso-login.spec.ts` (the IdP is mocked).
- **Enterprise SSO (workspace settings and staff tools)** — the workspace **Security** tab (`/teams`, also reachable at **`/settings/workspace/security`**, which is where the IdP test returns) is now visible to owners **and admins** (`TeamPermission.SSO_MANAGE`). The sign-in-method selector stays **owner only** (read-only for admins, who are told why); `Single sign-on (SAML)` becomes available there only for a verified domain whose SSO is enabled and tested, and the owner can pick it as a policy only then. Per verified domain the SSO card shows the **ACS URL** and **Entity ID** with copy buttons, a setup guide for Okta, Microsoft Entra ID, Ping and Google Workspace, the IdP form (metadata URL, uploaded metadata XML up to 256 KB, or manual entity id / https sign-in URL / certificate), the certificate expiry (with a warning inside 30 days), and **Test SSO connection** (sends the admin to the IdP and back with `?sso_test=passed|failed`), **Enable/Disable SSO** and **Remove connection**. While SSO is required the connection is locked, mirroring the server's 409s. Admins can configure, test and disable but **Enable SSO is the owner's** (the button explains this). The whole card is hidden while `enableSso` is off. **Staff ops panel** (`/api/v1/admin`, flag `pricingTiersEnabled`): `GET /teams/domains/:domain/sso` (support: setup, tested/enabled state, live SSO session count and the recent `SAML_*` team-audit trail; never the certificate; audited as a read), `POST /teams/domains/:domain/sso/disable` and `POST /teams/domains/:domain/sso/reset` (platform admin, step-up, `reason`/`ticketRef`). Both writes sign out the SSO sessions, put a domain that required SSO back to `ANY` (so nobody is locked out), write the team trail (`SAML_DISABLED` / `SAML_CONFIG_UPDATED`, `byStaff`) and the admin trail (`SAML_DISABLED` / `SAML_CONFIG_RESET`) in one transaction, log identifiers through Pino and send the risky-action alert email. In the admin Team workspaces tab each verified domain has **View SSO** (and an "SSO on" badge); platform admins also get **Disable SSO** and **Reset SSO setup** there. E2E: `frontend/e2e/workspace-sso.spec.ts`.
- **Feature announcements ("What's new")** — staff-authored, plan- and role-targeted product announcements in five placements: a **modal** (what's-new overlay), a **spotlight** (a callout pointing at a fixed UI anchor), a sticky **banner** (INFO / WARNING / CRITICAL), a nav **badge** on a sidebar entry, and the **What's New** tab in the notification bell (the changelog). Gated by `config.features.enableAnnouncements` (a code-config flag, in `development.ts` / `production.ts` / `test.ts`; **off in production** until switched on; no new environment variable). While off, `/api/v1/announcements` and `/api/v1/admin/announcements` answer `403 FORBIDDEN_FEATURE_DISABLED`, `GET /auth/me` returns `announcements: null` and the UI shows nothing. Backend: `backend/src/modules/announcements/` (user API, targeting, caches) and `backend/src/modules/admin/announcements-service.ts` (staff writes); frontend: `frontend/src/modules/announcements/` (runtime) and the **Announcements** tab of the staff panel (`frontend/src/modules/admin/components/AnnouncementsTab.tsx`).
  - **Targeting.** An announcement targets plan tiers (`targetPlans`: `ALL`, `FREE`, `PRO`, `TEAM`; `ALL` absorbs the rest), optionally workspace roles (`targetRoles`: `OWNER`, `ADMIN`, `MEMBER`; empty means every role, and a solo account counts as `OWNER`), and a schedule (`startsAt` / `endsAt`, UTC, checked at request time so a window needs no cache expiry). The server picks at most one modal, one banner and one spotlight per user (highest `priority`, then newest) plus every badge; the changelog is capped at 20 in the boot payload. Spotlights and badges reference fixed enums (`AnnouncementAnchor`, `AnnouncementNavKey`), never a free-form selector; a page opts in with `data-announce-anchor`. Bodies are plain text, rendered as text; a button link must be an in-app path or an `https` URL; a MODAL or SPOTLIGHT must be dismissible so a user can never be trapped.
  - **Zero-latency data plane.** The published, enabled list is cached three deep: an in-process copy (5 s), Redis (`announcements:active`, 5 min safety TTL) and PostgreSQL, with concurrent misses coalesced into one load (single-flight) and a generation guard so a load that began before an invalidation cannot repopulate the cache. Targeting is a pure in-memory function (`evaluateForUser`; a unit test holds 200 active announcements under 5 ms), and the result rides on `GET /auth/me` (`announcements`), so a page load needs no extra request or database query on the warm path (`fetchMe` already reads the workspace role in the same query as the profile). If Redis is down it falls back to PostgreSQL; a failure in the announcements path degrades to `announcements: null` and never stops the app from booting. `GET /announcements/boot` returns the same payload for cheap refetches.
  - **Dismissal and read state.** Per user, in PostgreSQL (`announcement_user_states`, the source of truth) and mirrored into a Redis hash (`announcements:state:{userId}`, 30 days). `POST /announcements/:id/dismiss` (idempotent; 409 if the announcement is not dismissible), `POST /announcements/:id/seen` and `POST /announcements/seen` only ever change the caller's own state (the user id comes from the session). A dismissed item never comes back, including after edits; staff must use **Re-announce**, which starts a new `reannounceEpoch` so every earlier dismissal and read mark stops counting without touching any rows. Dismissed items stay in the changelog drawer, marked read (it is history, not an interruption). Deleting an account deletes its rows.
  - **Control plane.** `/api/v1/admin/announcements` (`GET` list/detail with seen and dismissed counts: `SUPPORT_AGENT`; `POST`, `PATCH /:id`, `DELETE /:id` (archive), `POST /:id/publish`, `/:id/enable`, `/:id/reannounce`: `PLATFORM_ADMIN`; `POST /:id/disable`, the **emergency kill switch**: `SUPPORT_AGENT` and up). Every write needs step-up, a `reason` and (when `config.admin.requireTicketRef` is on) a `ticketRef`, and appends one `AdminAuditLog` row in the same transaction (`ANNOUNCEMENT_CREATED`, `_UPDATED` (with the changed field names), `_PUBLISHED`, `_KILL_SWITCH_TOGGLED`, `_REANNOUNCED`, `_ARCHIVED`). Edits use optimistic concurrency (`expectedVersion`; a stale edit answers 409). After a write commits, the cache is dropped and a content-free `announcements_changed` Socket.IO event tells connected clients to refetch. **How instant is the kill switch:** the Redis list and the serving instance's copy are dropped immediately and connected clients on that instance refetch at once; other instances serve from memory for up to 5 s, and clients connected to them refetch on the next tab focus (at most once a minute). There is no Redis adapter for Socket.IO, so the push does not cross instances.
  - **Tests.** Backend: `backend/src/modules/announcements/__tests__/` and `backend/src/modules/admin/__tests__/announcement*.test.ts` (targeting matrix, cache layers and invalidation, single-flight, dismissal isolation between users, RBAC and step-up for every staff route, audit atomicity). Frontend: unit tests beside the code and `frontend/e2e/announcements.spec.ts`. Announcements and their dismissals are platform-global or per-user, not tenant-scoped, so they are covered by user-isolation tests rather than the tenant-isolation suite. Apply the schema with `npm run db:sync`.
- **User feedback** — an in-app channel from users to the team (`backend/src/modules/feedback/`, `frontend/src/modules/feedback/`). The sidebar **Send feedback** button opens a modal with an optional category (**Bug**, **Feature request**, **General**), a message (up to 2,000 characters) and a one-line note that the browser and screen size are included. `POST /api/v1/feedback` (`CORE_APP:WRITE`, **5 per minute per user**, `config.feedback.submitLimitPerMinute`) stores the message, the page the user was on, the category and a `metadata` object: the browser's `userAgent`, the `viewport` (width and height) and the web `appVersion` (from `package.json`, injected at build time), plus the **`planTier`, which the server adds from the signed-in session**. The client cannot choose its plan: the metadata schema is strict, so a body that includes `planTier` (or any other unexpected key) is rejected with 400. Text fields are length-limited and refuse control characters. The feature is permission-based and behaves the same in the role-based and the tier-based workflow (it never checks `pricingTiersEnabled`).
  - **Triage.** Users with `ACCESS_CONTROL:READ` and `ROLE:READ` see **User Feedback** under the access-control menu (`/access-control/feedback`): New / Read / Archived / All tabs (counts always cover the whole inbox), a category badge on each entry, a collapsible **Technical details** section (plan, browser, window size, app version) and one-click **Mark read**, **Mark unread**, **Archive** and **Restore to New**. `GET /api/v1/feedback?status=NEW|READ|ARCHIVED` filters (default: all) and returns `counts`; `PATCH /api/v1/feedback/:id/status` (`{ status }`, same permissions; idempotent, answers `changed: false` when nothing changes) records who changed it and when (`statusUpdatedBy` / `statusUpdatedAt`) and logs the change by ids only (`[Feedback] status changed feedbackId=… by=… from=… to=…`). Existing entries become `NEW`. Apply the schema with `npm run db:sync`.
  - **Chat alert (optional).** Set `FEEDBACK_WEBHOOK_URL` (a Slack or Discord incoming-webhook URL; a secret, because the URL embeds a token) to ping the team for each new submission. The URL must be `https` on `hooks.slack.com`, `discord.com` or `discordapp.com` (`config.feedback.webhookAllowedHosts`); anything else stops the app at boot. The alert is sent **after the feedback is saved and is never awaited**: a 3-second timeout (`webhookTimeoutMs`), no redirects, and any failure is caught and logged as `[Feedback] webhook failed feedbackId=… kind=…`, never failing the user's request and never logging the URL or the message. It names the category, plan, page, a snippet of the first 200 characters (`webhookSnippetChars`) and the feedback id, with `@everyone`, `@here`, `<!channel>`, user mentions and link syntax defused; it contains **no name or email**. There are no retries (best effort); leave the variable empty to turn the alert off. Technical details are kept when an account is soft-deleted, like the rest of the entry.
- **Operational alerts** — a Slack or Discord channel for things that need a human, separate from the feedback channel. Set `OPS_ALERT_WEBHOOK_URL` (a secret, because the URL embeds a token); leave it empty to turn alerts off. The URL must be `https` on `hooks.slack.com`, `discord.com` or `discordapp.com` (`config.opsAlerts.webhookAllowedHosts`); anything else stops the app at boot. Code: `backend/src/shared/infrastructure/ops-alert.ts` (the sender), `chat-webhook.ts` (the Slack/Discord transport it shares with feedback), `alert-throttle.ts` (storm control) and `job-alert.ts` (background jobs). Alerts are **a pointer, not a record**: the structured log line at the call site (shipped to Axiom) stays the system of record, and an alert only says what kind of problem it is plus ids.
  - **What alerts.** `PAYMENT_WEBHOOK_REJECTED` (a Safepay webhook with an invalid signature: a forged call, or a rotated secret that breaks every real payment); `PAYMENT_WEBHOOK_FAILED` (processing a verified webhook threw a server-side error, so a paid user may not be upgraded; Safepay will retry); `PAYMENT_NEEDS_MANUAL_ACTION` (a renewal was paid for a workspace that was deleted, or has no subscription: money taken, nothing delivered); `JOB_FAILED` (a background job failed **for good**: every worker (email, auth email, and the subscription, news and watchlist crons) alerts only once its retries are used up, so a transient failure that BullMQ retries stays quiet; a job queued without retries alerts on its first failure); and `RISKY_ADMIN_ACTION` (every action in `RISKY_ADMIN_ACTIONS`: plan override, session invalidation, the market halt, force-removing a member, auth-policy and SSO resets, step-up lockout, a large credit adjustment, a **spend-limit override** and **switching an announcement on or off**; asking for the state it already has is a no-op and does not alert). Risky staff actions still also email `config.admin.alertEmails`; the two channels are independent, so an empty recipient list or a chat outage never blocks the other.
  - **Storm control.** One alert per kind and key per window (`config.opsAlerts.dedupeWindowSeconds`, 10 minutes), shared across instances through Redis (`SET NX EX`) and per process if Redis is not available. Anything held back is counted, and the next alert that goes out says `(+N suppressed since the last alert)`. The key is what the alert is about: the queue and job for a failing job, the team for a payment, the action and target for a staff action, so a failing queue is one alert, not one per job, while two different problems are never merged.
  - **Zero personal data.** An alert is a fixed sentence plus `name=value` details, and a value is printed only if it is a plain id (letters, digits and `_ . : -`, at most 80 characters). An email address, a name, a URL or a sentence cannot pass, whatever a caller hands in, and `@` and `<` are defused so nothing pings a channel. Errors are reported by class name (never the message, which can echo a recipient or a URL). Delivery is best effort and never throws: 3-second timeout, no redirects, and a failure is logged as `[OpsAlert] delivery failed kind=… status|kind=…`, never with the URL. The alert call sites are not awaited, so a chat problem cannot change a payment response, a webhook's retry behaviour or a staff action.

- **Node.js** ≥ 18

```bash
git clone https://github.com/Stock-App-Platform/StockPros_Hackathon.git
cd StockPros_Hackathon
```

```env
FEEDBACK_WEBHOOK_URL=   # optional Slack/Discord incoming-webhook URL pinged on each new feedback (https, hooks.slack.com or discord.com only)
OPS_ALERT_WEBHOOK_URL=   # optional Slack/Discord incoming-webhook URL for operational alerts (payments needing attention, failed jobs, risky staff actions); use a different channel from feedback
```

## Troubleshooting

- Verify all required environment variables are set (see the `.env` blocks above and each service's `.env.example`)
- Confirm Node.js, npm, and Python versions match the Prerequisites above
- Reinstall dependencies (`npm install` / `pip install -r requirements.txt`) if you see missing-module errors
- Confirm PostgreSQL and Redis are reachable at the URLs in your `.env` before starting the backend
